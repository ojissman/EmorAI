## Limitations (documented, deliberate)

- Scheduler boots at server start (instrumentation) — the sandbox's automatic restarts already loaded it; in dev, editing instrumentation.ts requires a restart to re-load.
- In-process, single-server timers only — multi-node deployments need external coordination; no distributed locking.
- No quota sync job: providers expose no quota API on this installation — unsupported, NOT fabricated (unknown job name is rejected 400).
- Alert delivery is record-only (AlertEvent rows surfaced via /api/ops/alerts): email/webhook wiring is future configuration.
- provider-health "2 consecutive unhealthy" escalation reads the previous successful run's result JSON (JobRun table as persistence); two concurrent same-job executions (manual while scheduled is in flight) each get their own row and the escalation check may treat the earlier one as "previous" — accepted edge.
