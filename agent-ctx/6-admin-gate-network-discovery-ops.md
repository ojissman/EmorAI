## Backend response-shape notes for the orchestrator

1. **`GET /api/ops/jobs` actual shape** (route landed in parallel): `{scheduler:{running, jobs:[{job, cadence}]}, runs:[JobRun], aggregate:{total24h, failed24h, perJob:{job:{lastStatus,lastStartedAt}}}}` — the task brief described "jobs list + aggregates"; the frontend was written against the REAL route file (initial `jobs`/`aggregates` assumption corrected before verification). No backend change needed.
2. **Model probe path is `/api/models/{rowId}/probe`** where rowId is the ModelConfig DB id (cuid), NOT the public modelId. Integrators must resolve the row id via `GET /api/models` first (the dialog does this).
3. `adoptionDraftFor` seeds contextWindow from the listing; the adopt schema rejects contextWindow < 1024 — the UI only sends it when ≥1024.
4. The ops jobs/alerts routes did not exist when the task was issued; they landed mid-task (scheduler via `src/instrumentation.ts`). The UI was built to tolerate their absence (error card + Retry) and now consumes the real shapes.
